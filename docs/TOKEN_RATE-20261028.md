# 2026-10-28：本地日志近似输出 TPS 验证

## 结论

可以从本机日志得到响应结束后更新的近似输出TPS；目前不宜把它直接替换为默认的“瞬时速度”。现场没有逐Token持久化增量，且部分条目时间窗过短，会把最近一次响应的估算值严重放大。更合适的后续试验是单独提供“本轮平均输出 ≈xxx/s”切换项，保留原用量口径。

本轮完成只读原型与验证，没有安装第三方程序、接入日常上位机或烧录固件。原型及复现命令见[tests/token_rate](../tests/token_rate/README.md)，汇总见[结构化证据](evidence/token-rate-20261028.json)。

## 来源与公式

已读取[用户分享的方案](https://chatgpt.com/s/t_6ae149f0e958819194591a12065a795c)，以及它引用的[codex-statusbar说明](https://github.com/dongyue-19/codex-statusbar/blob/main/README.zh-CN.md)和[TpsTracker实现](https://github.com/dongyue-19/codex-statusbar/blob/main/src/CodexStatusbar/TpsTracker.cs)。[官方Codex事件接口](https://learn.chatgpt.com/docs/app-server#events)提供条目流式增量、条目完成和用量通知，但这不意味着另一个进程已经接入桌面端当前对话的响应流。本轮检查实际落盘数据，不接管当前Codex进程。

```text
本轮近似输出 TPS = 本轮已报告 output_tokens 合计
                  ÷ 已完成 Reasoning / AgentMessage 时间窗并集的秒数
```

推理token已包含在output_tokens中，不重复相加；工具时间窗不加入分母，重叠模型窗口只计一次。现代`token_usage_record.usage`按(thread_id, turn_id, response_id)去重，双载体中的旧token_count不再累加。这个原型不支持仅有旧载体的TPS，也不读取账号认证或发送模型请求。

另试算“最近响应TPS”：用当前响应输出量除以上一个用量边界后新完成的模型窗口；跨边界的窗口不强行匹配。两种指标均只在响应边界更新，不按扫描次数生成新数值。没有完整轮次起点、模型时间为零/反向或计数冲突时返回不可用。

## 验证结果

| 项目 | 观察或结果 |
| --- | --- |
| 构造检查 | 24项通过：长工具间隔、窗口重叠、重复响应、相同数值的不同响应、双载体、分页重放、推理子项、非法/缺失时间、并发来源等 |
| 最终历史快照 | 采样8份最近修改日志，观察20轮，其中13轮具备本轮估算条件；5轮计时/计数校验未通过，2轮等待匹配用量或条目 |
| 可计算轮次的本轮估算 | 约40.1–362.2 tok/s，中位数约93.6；这不是同模型性能基准，也不是流式真值 |
| 首轮现场观察 | 120.041秒、同一来源3次更新；相邻更新间隔11.653–32.119秒；读出延迟中位数127ms |
| 最终现场复查 | 60.024秒、两个来源各1次更新；读出延迟中位数162.5ms。来源分别统计，不把跨对话间隔当作某个对话的更新频率 |
| 极短窗口反例 | 一份响应的模型窗口仅1ms，最近响应公式得到920000 tok/s；同一时刻整轮公式约406.7 tok/s。不能把前者解释为实际模型速度 |
| 流式真值 | 未取得原始响应流或服务端解码计时，未量化本机估算误差 |

首轮探索原型的来源归属已回查三个用量时间点，确认来自同一对话；最终版本另增加并发来源分组与对应测试，防止混淆不同会话的更新间隔。探索、最终快照及极短窗口复查发生在不同时间，活动日志持续增长，不将不同快照的计数混为一份静态数据。

工具耗时、网络与等待时间会影响使用者看到的任务进度；客户端条目起止不等于服务端完整解码区间。官方输出还可能包含工具调用参数，而选中的模型条目窗口未必完整覆盖这部分生成时间。缺少流式真值时，不能把第三方作者的误差测试直接当成本机精度，也不靠平滑或上限截断把异常变成“正确速度”。

## 接入判断

1. 现有tok/min表示最近一分钟的输入与输出消耗；输出TPS表示产出速度，是两个不同指标，不能把现有数值直接除以60。
2. 优先尝试本轮平均输出，明确显示`≈`及“响应结束后更新”，等待/工具执行期间标记为保留值，无法计算时显示`--/s`。最近响应模式仍需解决短窗口和计时覆盖问题，不宜直接设为默认。
3. 若替换底栏数字，曲线必须另保留tok/min单位，避免把当前一分钟用量曲线误读为输出速度曲线。
4. 输入TPS与账号全设备瞬时速度缺少对应实时计时/数据，本轮不提供这两个指标。

## 独立命令行试用

按用户要求新增[命令行面板](../tests/token_rate/live_console.py)，已在本机打开`CodeX Token Speed - Live Test`窗口并跟随本次真实会话更新。主数字是最近5份合格响应的时间加权速度，再以开源实现同样的0.35系数平滑；下行给出有效样本的本轮加权均速。真实输入/输出Token总数独立统计，计时不适合测速的响应也不会丢失用量。

短于250ms的响应不单独作为测速样本，至少积累1秒有效模型时间再产生速度；其余计时不完整或暂不能匹配的情况在内部处理，保留最近测量并显示更新时间，后续正常响应继续更新。原1ms反例已加入回归检查：速度不跳高、真实Token仍累计、下一响应可恢复；零时长不再使整轮后续样本失效。面板不向用户输出调试异常。

现有24项分析检查及10项命令行检查共34项通过；实测窗口存在且后续真实测量计数持续推进，见[命令行证据](evidence/token-rate-console-20261028.json)。界面每0.5秒刷新，数值只在响应边界更新，不模拟逐秒解码速度。生产上位机与固件尚未接入这个实验面板。

随后按用户意见补充轮次结束归零与快慢统计并列：当前速度在task_complete或turn_aborted后归零，最近测速、本轮均速和Token累计不清空；迟到用量继续累计但不能重启已完成轮次的速度。近60秒输入/输出消耗跨轮次计算，在记录移出60秒窗口后自然归零；这里仅统计指定会话，上位机的本机汇总覆盖范围另行保留。开源实现和本面板的EMA系数相同，但前者平滑整轮累计均速，后者平滑最近5个合格响应的加权均速，不能称为算法完全一致。

新增5项生命周期检查后共39项通过；真实已完成轮次回放确认当前速度0、最近测速与累计仍保留，见[生命周期证据](evidence/token-rate-lifecycle-20261028.json)。命令行窗口已换到包含这些行为的版本。
